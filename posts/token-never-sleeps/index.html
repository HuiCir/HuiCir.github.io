Token Never Sleeps：把长时任务从一次对话，变成可接力的工作流

TNS 是一个为 Claude 设计的 long-running 插件与 runner。它的目标不是“让模型更聪明”， 而是让一个真实任务在数小时尺度上依然可推进、可恢复、可验证。这篇文章也是新博客主页上的第一篇系统文章。

2026-04-17 12 min read GitHub

大模型最擅长的是短时、集中的推理与生成，但工程任务往往不是这样展开的。一个真实的软件任务会持续数小时， 需要查仓库、改代码、跑测试、失败后回退、在 token 或配额不足时暂停，然后在下一轮继续。 如果仍然把它想象成“一次 prompt 解决一切”，系统设计从一开始就会错位。

Token Never Sleeps 想解决的，就是这种错位。它从一个 `task.md` 出发，让 Claude 在外部 runner 的调度下， 以分段、可交接的方式持续推进工作，而不是把所有上下文和所有希望都压进单个会话里。

为什么这个项目值得单独做

Claude 插件本身可以扩展命令、hook 和 agent，但它并不会天然解决“跨会话连续工作”这个问题。 一旦遇到 usage limit、长时间空转、上下文膨胀或单轮执行过重，系统就需要一个外部调度者来接管节奏。

核心判断

长时 agent 不是更长的 prompt，而是更好的 runtime。你需要 fresh context、状态文件、验证环节和恢复机制。

TNS 的工作方式

默认流程很克制，也很工程化：

  • 读取工作目录下的 `task.md` 和 `tns_config.json`。
  • 由 runner 选择当前 section，调用执行 agent 完成一个明确的增量。
  • 若结果达到提交条件，切给 verifier 做独立验证，而不是让执行者自我放行。
  • 把状态、活动日志和 handoff 留在磁盘上，下一轮可以在 fresh context 中继续。
  • 遇到 usage-limit 风格错误时，自动回滚到最近 clean state，避免脏工作区继续滚雪球。

我最看重的四个设计点

1. Runner 在模型外部

TNS 的重点之一是把调度逻辑放到 `scripts/tns_runner.py`。这意味着“继续下一轮”“检查 quota”“通知远端” 这些动作不依赖某个会话还活着，也不要求 agent 记住全部历史。

2. Executor / Verifier 分离

这是最接近真实软件流程的部分。执行 agent 负责推进，verifier 负责用更冷静的视角确认结果是否真的通过。 否则很容易出现“自己写、自己觉得没问题”的乐观偏差。

3. Workflow 可配置

TNS 现在不只是一对固定角色。`workflow.agents` 可以把系统扩展成 planner、reviewer、triager 或 release-check 等节点，并基于结构化 JSON 输出决定下一跳。这个抽象让它更像一个轻量 runtime，而不是一次性脚本。

4. 配额意识不是附属功能

token 或 usage 窗口从来不是“边角异常”，它是长时代理系统的主约束之一。TNS 用 rolling usage 与外部 provider 两种模式去估算余量，让调度器在资源紧张时也能做出保守决策。

一个很实际的 quickstart

最小配置只需要两个文件：

{
  "workspace": "/absolute/path/to/project"
}
# Task

## Section 1
Define the target change.

## Section 2
Implement and verify it.

然后在 Claude 内调用：

/tns-status --config tns_config.json
/tns-start run --config tns_config.json

如果你希望 runner 自己在 `tmux` 里长期存活，也可以切换到 `run-tmux`。这类细节看起来朴素， 但正是“能不能连续跑一夜”的分水岭。

它和普通 README 型项目的区别

很多 agent 项目止步于 demo：给你一个漂亮概念、一段 prompt、一个 CLI，然后默认任务会自己成功。 TNS 相反，它把失败、暂停、恢复、远程通知、clean state、handoff 这些“麻烦但必需”的部分放到了系统中心。

这也是我想把它作为这个博客首篇文章的原因。它代表了我偏好的工程方向：不是追求抽象上更大的智能， 而是把已经可用的能力组织成一个在现实世界里更可靠的生产机制。
