Essay 002 · Codex Architecture

Codex 的 agent loop：薄循环，厚 harness

Codex 最值得看的地方，不是“模型会不会调用 shell”，而是它如何把一次模型输出变成可治理的工程动作。 agent loop 本身很薄：模型提出下一步，工具返回观察，直到任务结束。真正承重的是 harness： 它管理上下文、权限、沙箱、工具协议、历史和恢复路径。

2026-04-20 11 min read OpenAI source

很多 coding agent 的介绍会从模型能力开始：能不能读项目、能不能写补丁、能不能跑测试。这个角度没错，但它容易漏掉更关键的问题： 当模型决定“下一步要做什么”之后，谁来决定这一步是否可以真的发生？

Codex 的答案不是把所有责任继续压给模型，而是在模型和真实机器之间放一层 harness。模型负责生成意图； harness 负责把意图翻译成有边界的动作，并把动作结果放回下一轮推理。这个分工，是 Codex agent loop 的核心设计哲学。

一句话

Codex 不是“让模型操作你的机器”，而是“让模型通过一个受控运行时请求改变你的机器”。

Loop 很简单，也因此容易被误读

OpenAI 的 agent loop 图可以概括成几步：用户提出任务，模型生成回复；如果模型需要更多信息或需要执行动作， 它发起工具调用；运行时执行工具，把结果追加回上下文；模型基于新信息继续推理；直到它不再调用工具，而是返回 assistant message。 

user task
  -> model inference
  -> tool call
  -> tool result
  -> model inference
  -> assistant message

这条 loop 看起来几乎朴素，朴素到很多 demo 会把它写成十几行代码：拼 prompt、调模型、看到 shell command 就执行、 把 stdout 塞回去，再调一次模型。但 Codex 不是这样理解 agent loop 的。对一个本地 coding agent 来说， loop 不是一段控制流，而是一条责任链。

代码修改、依赖安装、测试执行、文件删除、网络访问，这些都不是“文本输出”。它们会改变用户的工作区。 所以问题不能停在“模型下一步想做什么”，还必须继续问：这一步在什么目录执行？能写哪些路径？需不需要审批？ 失败后是否允许换一种权限重试？工具输出如何记录？下一轮模型看到的到底是哪一种状态？

Turn 不是 prompt，而是一次工程事务

Codex 官方文章里有一个很重要的细节：一次 conversation turn 可以包含多次模型推理和多次工具调用。 这意味着 turn 不等于一段 prompt。它更像一次工程事务：从用户输入开始，到模型给出最终 assistant message 结束； 中间发生的工具调用、审批、失败、恢复、历史写入，都属于这次 turn 的一部分。

在 openai/codex 的公开源码里，run_turn() 进入模型采样之前已经做了很多运行时工作： 更新上下文、处理 skills 和 plugins、整理 MCP 工具、注入环境信息、维护 telemetry、必要时触发 compaction。 这些东西看起来都不属于“模型智能”，但它们决定了模型到底在什么现实条件下工作。

这也是为什么“把 prompt 写好一点”不能替代 harness。prompt 可以提醒模型小心，turn context 则把小心变成可执行的边界： 当前目录是什么、沙箱策略是什么、审批策略是什么、可用工具是什么、用户和 developer instruction 的优先级是什么。

工具调用是意图，不是副作用

Codex loop 里最重要的边界，是把“工具调用”与“工具执行”分开。模型可以提出一个 tool call， 但这个 tool call 不应该天然拥有改变文件系统的权力。它先是一份意图描述：工具名、参数、调用 ID，以及它在当前 turn 里的位置。

这个区别听起来细，但它决定了系统能否治理副作用。假设模型想删除文件。没有 harness 的设计里， “删除文件”可能只是 shell 字符串里的几个字符；运行时只能执行后再看结果。Codex-style 的设计里， 删除动作会先进入调度和审查路径：它要删哪里？是否递归？是否越过工作区？是否需要用户批准？如果被拒绝，拒绝理由如何回到模型上下文？

OpenAI Responses API 的 function calling 协议也体现了这个边界：模型返回 function_call， 应用执行自己的函数，然后把 function_call_output 交回模型。API 不替应用执行本地工具； 执行权仍然在 harness 手里。

ToolOrchestrator 承载的是治理逻辑

在 Codex 源码里，工具执行的核心入口之一是 ToolOrchestrator。它不是简单的 executor。 它把工具运行放进统一顺序：先判断 approval requirement，再选择 sandbox，执行第一次 attempt； 如果 sandbox 拒绝，并且策略允许，再请求升级并重试。 

approval
  -> sandbox selection
  -> first attempt
  -> denial handling
  -> optional approval for escalation
  -> retry with adjusted sandbox

这套顺序背后的哲学很清楚：模型不直接拥有现实动作，工具也不绕过运行时策略。所有会改变环境的动作， 都必须穿过同一个控制面。审批、沙箱、网络策略、失败原因、telemetry 和重试路径不散落在各个工具里， 而是由 harness 统一组织。

这就是“厚 harness”的含义。厚，不是代码多；厚，是责任重。它把语言模型不擅长稳定承担的事情拿出来： 权限判断、状态管理、边界执行、错误恢复、审计记录，以及不同客户端之间的一致协议。

为什么同一套 harness 要服务多个入口

OpenAI 后续关于 App Server 的文章，把这个设计从产品侧解释得更明显：VS Code extension、TUI、桌面入口都需要驱动同一套 harness。 这不是为了复用几段工具代码，而是为了复用同一套 agent runtime。

如果每个客户端都各自实现 loop，就会很快分叉：一个入口的审批语义不同，另一个入口的工具输出格式不同， 第三个入口的 session 恢复方式不同。对普通聊天产品来说，这可能只是体验差异；对 coding agent 来说， 这会变成安全边界和状态一致性问题。

所以 App Server 的价值不是“给 UI 一个接口”这么简单。它把 harness 的事件流、审批、diff、工具结果和 session state 变成客户端可以消费的协议。UI 可以不同，但改变工作区的那套规则必须尽量一致。

厚 harness 的代价

这套设计当然有代价。调试一个失败的 Codex 任务，不能只看模型最后说了什么。你还要看 turn context、 输入历史、工具调用、审批事件、沙箱策略、工具输出、compaction 和最终写入的状态。

但这正是 coding agent 和普通聊天机器人的分界。聊天机器人的错误通常停留在文本里；coding agent 的错误可能落到文件系统、 依赖环境、网络请求和 git history 里。把复杂度留在 harness，而不是把复杂度交给模型自觉，是更稳的工程选择。

awesome-harness 只是一个教学切片

awesome-harness 的意义不在于复刻 Codex。它只是把上面的边界切成一个很小的可运行例子：同一个任务，一边让模型吐 shell 字符串并直接执行； 另一边让模型吐 typed tool call，再由 policy 和 tool registry 决定是否执行。

任务里故意放了一个危险但常见的词：cleanup。常规 shell-agent 把它扩成 rm -rf *， 结果报告写出来了，项目上下文也被删掉了。harness-agent 则先拒绝递归删除工作区，再允许删除明确的 tmp/cache.txt。这个 demo 只说明一件事：结构化动作给了运行时介入的机会。 

Conventional shell-agent:
  model: rm -rf *
  executor: runs it
  result: workspace context is gone

Codex-style harness-agent:
  model: delete_path {"path": ".", "recursive": true}
  scheduler: deny
  model: delete_path {"path": "tmp/cache.txt", "recursive": false}
  scheduler: allow
  result: source stays, cache is removed

这个例子应该被放在它该在的位置：它是显微镜，不是主题本身。主题仍然是 Codex harness 的设计哲学： 把模型的不确定输出转成可审查的动作，把危险副作用挡在执行前，把真实结果送回下一轮推理。

还要保留一个边界

harness 也不是魔法安全层。官方 agent loop 文章提到，Codex 注入的 sandbox developer message 约束的是 Codex 提供的 shell tool； MCP 等外部工具需要各自负责 guardrails。换句话说，harness 可以统一很多治理逻辑，但一旦接入外部能力， 每种能力仍然要明确自己的权限模型和失败语义。

这点很重要。好的 agent runtime 不是宣称“工具都安全”，而是让每个工具在进入现实世界之前都有明确的协议位置： 它是谁、要做什么、参数是什么、谁批准、怎么执行、失败如何返回、结果如何被记录。

回到那条 loop

Codex agent loop 表面上很薄：模型、工具、观察、再模型。真正值得学习的是 loop 外面的 harness。 它承认模型强在生成和推理，但不把权限、状态和副作用治理交给模型自由发挥。它把模型输出降落成工程系统可以处理的对象。

这也是 Codex 和许多 agent demo 的根本差别。demo 往往证明“模型能调用工具”；Codex 更关心“模型调用工具之后， 这件事如何在真实工作区里被约束、恢复、解释和复用”。薄 loop 让模型持续前进，厚 harness 让前进这件事不至于失控。
