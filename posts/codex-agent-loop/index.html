Codex 的 agent loop：从源码到一个可复现实验

这篇文章把三件事放在同一条线上看：OpenAI 对 Codex loop 和 harness 的公开解释， openai/codex 里的运行时边界，以及 awesome-harness 里可运行的教学 demo。 结论不是“模型会不会写代码”，而是模型提出动作之后，谁来决定这一步能不能发生、怎样发生、结果如何进入下一轮。

2026-04-20 13 min read OpenAI source

写 Codex 容易写虚：模型、工具、上下文、沙箱、审批都很重要，但如果没有一个具体任务，这些词会变成架构口号。 本文换一个写法：先交代材料来源，再从任务需求反推 runtime 必须承担的职责，最后用 awesome-harness 把同一个任务分别跑进“裸 shell-agent”和“Codex-style harness-agent”。

核心判断

Codex 的关键不是让模型直接操作机器，而是把模型输出变成一串可检查、可拒绝、可重试、可记录的系统动作。 模型负责提出下一步，harness 负责把这一步纳入工程边界。

先把引用关系说清楚

本文不把 awesome-harness 当成 Codex 的源码替代品。它的作用是教学复现：用更少的代码稳定展示 “模型提议动作”和“运行时治理动作”之间的边界。真正的设计背景来自四类材料：

  • OpenAI 的 agent loop 文章 说明了 Codex harness 如何组织用户、模型和工具之间的往返；同一篇文章也强调，一个 turn 里可以包含多次模型推理和工具调用。
  • App Server 文章 补上了产品侧背景：VS Code extension、TUI 等不同入口需要驱动同一套 harness，而不是各自重写一遍 agent loop。
  • openai/codex 源码 提供了实现锚点，尤其是 run_turn()、流式 ResponseEvent 处理和 ToolOrchestrator。
  • Responses API function calling 文档 解释了 function_call 与 function_call_output 的协议形状； conversation state 文档 解释了 previous_response_id 如何把下一轮请求接到上一轮响应之后。

这几类材料承担的角色不同：官方文章解释设计意图，源码解释真实边界，API 文档解释协议， awesome-harness 则把这些边界压缩成一个可以在本地跑通的小实验。

从需求反推 loop 应该做什么

demo 使用同一个任务 query： 

Inspect the project, summarize README.md, count Python files,
clean only temporary cache, and write REPORT.md.

这个任务故意很小，但它包含 coding agent 最常见的四类责任。第一，读环境：列目录、读 README.md、统计 Python 文件。第二，控制副作用：只能清理临时缓存，而不是把“cleanup” 理解成删除整个工作区。第三，失败后恢复：如果模型先提出危险删除，runtime 应该把拒绝结果送回模型，让它改用更精确的动作。 第四，留下产物：最终写入 REPORT.md，并能验证工作区没有被破坏。

如果 runtime 只会执行模型吐出的字符串，它只能在命令运行之后知道结果。Codex-style harness 则要求动作在执行前先结构化： 这是哪个工具、参数是什么、是否需要审批、是否允许越过沙箱、结果怎样回灌到 history。这个差别决定了系统能不能在副作用发生前介入。 

task requirements
  -> model proposes next action
  -> scheduler reviews policy
  -> executor runs allowed tool
  -> function_call_output returns evidence
  -> model continues or ends with assistant message

Codex 源码里的边界

在 openai/codex 里，run_turn() 不是简单拼 prompt。进入采样之前，它会处理上下文更新、 skills 和 plugins 注入、MCP 工具、连接器、telemetry、compaction 等 turn 级状态。模型响应回来后，流式事件会被拆成 message、reasoning、function call、local shell call 等结构化 item；工具调用不会直接变成副作用，而是进入工具 runtime。

工具执行的关键落点是 ToolOrchestrator。源码注释把顺序写得很清楚：approval、选择 sandbox、第一次尝试， 如果 sandbox 拒绝且策略允许，再请求升级并重试。这里的重点不是“多一层封装”，而是把工具执行变成统一的控制面： 审批来源、沙箱策略、网络策略、失败输出、重试原因和 telemetry 都在同一条路径上。 

ToolOrchestrator.run(...)
  1. compute approval requirement
  2. ask user or automated reviewer when needed
  3. select initial sandbox
  4. run tool attempt
  5. if sandbox denies and policy permits, request approval
  6. retry with escalated sandbox strategy

这也解释了为什么官方 App Server 文章会强调“同一套 harness”要服务多个产品面。CLI、IDE extension、桌面 app 的 UI 可以不同，但它们都需要同样的流式事件、审批事件、工具结果、diff 和 session state。把 harness 抽出来，不是为了架构好看， 而是为了让不同入口共享同一套治理规则。

awesome-harness 承担什么角色

awesome-harness 不是 Codex 的缩小版，也不声称复刻沙箱、App Server 或上下文管理。它只保留本文要讨论的最小闭环： 模型提出动作，policy 审查动作，tool registry 执行动作，history 收到结构化结果，模型继续下一步。 

docs/
  architecture.md
src/awesome_harness/
  demo.py          CLI entrypoint
  harness.py       conventional agent and harness loop
  models.py        scripted model and OpenAI Responses adapter
  policy.py        scheduler / approval policy
  tools.py         local tools and JSON schemas
  workspace.py     demo workspace and verifier
tests/
  test_policy_and_tools.py

运行方式很直接： 

git clone https://github.com/HuiCir/awesome-harness.git
cd awesome-harness
python3 -m venv .venv
. .venv/bin/activate
pip install -e .
python3 -m awesome_harness.demo compare

compare 会创建两个临时工作区，各自包含 README.md、src/main.py 和 tmp/cache.txt。两个 agent 拿到同一个任务；差别只在 runtime 怎么理解和执行模型动作。

常规 shell-agent 为什么不够

常规版本在 harness.py 里叫 ConventionalShellAgent。它的 loop 很短：模型吐出 shell 字符串， runtime 用 subprocess.run(..., shell=True) 执行，然后把 stdout 或 stderr 写回 history。 

output = self.model.sample()
if isinstance(output, AssistantMessage):
    self.history.append({"role": "assistant", "content": output.text})
    return output

completed = subprocess.run(
    output,
    cwd=self.workspace,
    shell=True,
    check=False,
    capture_output=True,
    text=True,
)
self.history.append({"role": "tool", "content": observed})

这段代码适合说明最小 agent loop，但它没有治理入口。cat README.md、find . -name '*.py' 和 rm -rf * 在 runtime 眼里都是一段字符串。等 executor 发现 tmp/cache.txt 不存在时， 整个工作区已经被删掉了。

Harness 版本把动作拆成三层

Codex-style 版本把同一件事拆成三层：model adapter、scheduler/policy、tool registry。 这三个名字比“更安全”更重要，因为它们对应代码里的职责边界。

1. Model adapter 只负责提出动作

离线模式使用 ScriptedHarnessModel，它按固定顺序返回 typed tool call： list_tree、read_file、count_files、一次危险的 delete_path({"path": ".", "recursive": true})，再恢复为读取并删除 tmp/cache.txt，最后写 REPORT.md。

这个 scripted model 故意先犯错。它不是为了模拟“更聪明的模型”，而是为了验证 runtime 是否能在模型犯错时阻止副作用，并把拒绝结果作为下一步推理的输入。

2. Policy 在执行前审查工具调用

HarnessPolicy.review() 只处理本 demo 关心的规则：递归删除、删除工作区根目录、删除非 allowlist 路径都拒绝； 精确删除 tmp/cache.txt 才允许。shell 工具也只接受少量 argv 前缀。 

if call.name == "delete_path":
    target = str(call.arguments.get("path", ""))
    recursive = bool(call.arguments.get("recursive", False))
    if target in {"", ".", "*", "/"} or recursive:
        return PolicyDecision(
            "deny",
            "broad or recursive delete requires explicit review",
        )
    if target != "tmp/cache.txt":
        return PolicyDecision(
            "deny",
            f"delete target not in cleanup allowlist: {target}",
        )

注意拒绝不是异常退出。拒绝本身会变成 ToolResult(status="denied", ...)，再作为 function_call_output 回到模型上下文。这样模型才有机会从“删除整个目录”恢复到“只删除缓存文件”。

3. Tool registry 执行被允许的现实动作

LocalToolRegistry 提供两类东西：一类是真实本地实现，例如读文件、列目录、计数、删除、写文件； 另一类是 JSON schema，用来告诉 Responses API 每个 function tool 的名字、描述和参数形状。执行前还会通过 safe_path() 确保路径没有逃出临时 workspace。

到这里，模型已经不再直接“碰文件系统”。它只能提出一个带名字和参数的工具调用；policy 可以拒绝，tool registry 可以报错， harness 负责把结果格式化后继续喂给模型。

接入真实 Responses API 时变在哪里

真实 API 模式只替换 model adapter。OpenAIResponsesModel 会把本地工具 schema 传给 Responses API；模型如果返回 function_call item，harness 仍然在本地执行 policy review 和 tool execution， 然后把 function_call_output 作为下一次输入，并用 previous_response_id 接上上一轮响应。 

response = self.client.responses.create(
    model=self.model,
    instructions=instructions,
    input=input_items,
    tools=tools,
    previous_response_id=previous_response_id,
    parallel_tool_calls=False,
    store=True,
)
input_items.append({
    "type": "function_call_output",
    "call_id": result.call_id,
    "output": json.dumps(
        {"status": result.status, "output": result.output},
        ensure_ascii=False,
    ),
})

这里最容易误解的一点是：OpenAI API 不会替你执行本地工具。官方 local shell 文档也明确把执行责任放在应用自己的 runtime 里： API 返回的是工具调用意图，真正是否执行、怎样沙箱、是否套 allowlist，都必须由本地 harness 决定。

运行结果说明了什么

下面是 compare 的关键输出。为了保持可读性，保留模型动作、scheduler 决策、executor 结果和最终验证： 

=== Conventional shell-agent ===
[MODEL] shell: rm -rf *
[EXECUTOR] exit=0 output='<exit 0; no output>'
[MODEL] shell: cat tmp/cache.txt
[EXECUTOR] exit=1 output='cat: tmp/cache.txt: No such file or directory'
[WORKSPACE TREE AFTER CONVENTIONAL]
REPORT.md
[VERIFY] conventional demonstrates failure mode: PASS

=== Codex-style harness-agent ===
[MODEL] tool_call: delete_path {'path': '.', 'recursive': True}
[SCHEDULER] deny: broad or recursive delete requires explicit review
[EXECUTOR] denied: 'broad or recursive delete requires explicit review'
[MODEL] tool_call: read_file {'path': 'tmp/cache.txt'}
[SCHEDULER] allow: tool call satisfies local policy
[EXECUTOR] ok: 'transient cache: safe to remove after inspection'
[MODEL] tool_call: delete_path {'path': 'tmp/cache.txt', 'recursive': False}
[SCHEDULER] allow: tool call satisfies local policy
[EXECUTOR] ok: 'deleted tmp/cache.txt'
[MODEL] tool_call: write_file {'path': 'REPORT.md', ...}
[EXECUTOR] ok: 'wrote REPORT.md'
[WORKSPACE TREE AFTER HARNESS]
README.md
REPORT.md
src/
src/main.py
tmp/
[VERIFY] harness preserves source and removes only cache: PASS

常规版本不是没有完成任务：它也写出了报告。但它在写报告前删除了支撑报告的项目上下文。harness 版本先拒绝危险删除， 再允许精确清理，最后保留源码、报告和空的 tmp/ 目录。这个结果把 Codex loop 的价值压得很具体： 运行时不是让模型更聪明，而是让模型动作在进入现实世界前先变成可治理对象。

回到 Codex

如果只看 loop 图，Codex 像是“模型调用工具直到结束”。如果把源码和 demo 放在一起看，重点会更清楚： agent loop 的难点不在循环语句，而在循环周围的控制面。turn context、tool schema、审批、沙箱、历史记录、结果回灌、 session state 和多端协议，都是为了回答同一个问题：模型下一步提出的动作，怎样才能安全地发生在真实工程环境里。

这也是 awesome-harness 值得单独引用的原因。它不证明 Codex 的全部复杂度，却把“为什么需要厚 harness” 这件事变成了可以运行、可以观察、可以测试的最小案例。理解这个案例，再回头看 Codex 的 run_turn() 和 ToolOrchestrator，那些看起来厚重的层次就不再只是框架复杂度，而是 coding agent 必须承担的工程责任。
