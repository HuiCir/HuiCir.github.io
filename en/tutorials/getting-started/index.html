Getting Started with TNS

Build a runnable TNS workspace from scratch in 10 steps. By the end of this tutorial you'll understand the core loop: init → compile → doctor → run → status.

Estimated time: 15 minutes Requires Node.js 22+ Requires claude CLI

Prerequisites

Before starting, make sure your environment meets these requirements:

  1. Install Node.js 22 or later

    TNS is a TypeScript npm package and needs a Node.js runtime.

    node --version
# Should output v22.x.x or higher

  2. Verify the claude CLI is in your PATH

    TNS invokes agents through the claude CLI. Run this to confirm:

    claude --version
# Should output a version number

  3. (Optional) Install tmux

    tmux is not required, but recommended for managed runner mode. On macOS: brew install tmux.

Step 1: Install TNS

npm install -g token-never-sleeps
tns help

After a global install, the tns command is available in your terminal. tns help lists all subcommands.

Step 2: Initialize a workspace

Use tns init to create a new workspace. This generates task.md, tns_config.json, and the .tns/ state directory.

tns init --workspace ./hello-tns
cd ./hello-tns
ls -la

You'll see this file structure:

hello-tns/
├── task.md              # Task description (you write this)
├── tns_config.json      # Workspace configuration
└── .tns/                # Runtime state directory

Step 3: Understand task.md

task.md is the core input to TNS. It describes the task goal, section breakdown, and acceptance criteria. A good task.md should:

  • Have a clear goal: state what to accomplish in one sentence.
  • Verify each section: every section needs explicit inputs and acceptance conditions.
  • Define clear boundaries: don't let one section handle exploration, implementation, and QA simultaneously.

Open task.md — you'll find a template. Edit the goal and sections, then save.

Step 4: Understand tns_config.json

tns_config.json controls workspace behavior. Key fields:

  • workspace — path, name, template info.
  • permissions — permission profiles and section-to-profile mappings.
  • monitor — watchdog heartbeat and agent timeout settings.
  • program — optional explicit FSM program.

For first-time use, the default config works well. Later you can optimize it with tns compile --synthesize.

Step 5: Compile

tns compile turns task.md and tns_config.json into a structured orchestration program:

tns compile --config ./tns_config.json

The output file .tns/compiled/program.json contains:

  • Task sections and required inputs
  • Bridge files and state files
  • Lifecycle and watchdog settings
  • Permission profiles and approval tags
  • Validators and command hooks

After compilation, the executor and verifier no longer need to "guess" the task structure — everything is explicit in the contract.

Step 6: Run doctor diagnostics

Before the first run, run tns doctor:

tns doctor --config ./tns_config.json

Doctor checks:

  • Config syntax and field completeness
  • Required binaries (node, claude, optional tmux)
  • Workspace directory structure and permissions
  • Preflight conditions

If doctor reports any issues, fix them before continuing.

Step 7: First run

Use the --once flag for a single-step run to observe the full TNS loop:

tns run --config ./tns_config.json --once

During the run you'll see:

  1. The runtime selects the current section
  2. The executor agent is invoked to process that section
  3. The verifier agent checks the output and produces a review
  4. Policy decides the state transition based on validation results

Step 8: Check status

After running, use tns status to inspect the workspace's current state:

tns status --config ./tns_config.json

Status reports:

  • Completion state of each section
  • Any freezes or pending approvals
  • Runtime heartbeat and active agent info
  • Artifact and lock states

Step 9: Monitor long tasks

For multi-round tasks, use tns btw for read-only observation (doesn't contend for the workspace lock):

tns btw --config ./tns_config.json --events 12 --reviews 5

Use tns trace to view recent event history:

tns trace --config ./tns_config.json --limit 40

Step 10: Recovery and cleanup

If a task is interrupted (process death, network failure, etc.), use tns recover to clean up residual state:

tns recover --config ./tns_config.json
# For forced cleanup:
tns recover --config ./tns_config.json --force

After recovery, you can resume directly — TNS restores context from the state files in .tns/.
