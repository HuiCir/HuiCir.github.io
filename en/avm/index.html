Token Never Sleeps Agent Virtual Machine

TNS AVM is a deterministic, file-system-stateful agent orchestration runtime. It compiles natural-language tasks into explicit machine contracts, then manages executor, verifier, permissions, validators, watchdog, and recovery paths through an external loop.

2026-04-28 Source: /root/TNS_AVM_TECHNICAL_REPORT.md npm v1.0.2

Abstract

TNS AVM provides a recoverable, verifiable, auditable virtual machine layer for long-horizon Claude agent workflows. It defines a finite-state execution engine, lightweight ISA, staged validators, permission profiles, resource locks, watchdog heartbeat, and a file-system state bus. Inputs are task.md and tns_config.json; outputs are .tns/compiled/program.json and a set of runtime state files.

Design claim

The core constraint of long-horizon agent work isn't "how far can a model think in one pass" — it's whether the task can keep making progress across fresh contexts, failures, interruptions, permission gates, and verification checkpoints.

Problem model

TNS AVM directly addresses five classes of long-task risk:

  • After process death, network failure, or usage limits, work must resume from disk state.
  • Open-ended agents drift toward scope creep; the runtime must enforce section boundaries.
  • Shell, file, and network capabilities need per-stage control, not a blanket grant.
  • Output must pass systematic acceptance through verifiers, validators, and command hooks.
  • Debugging requires replayable programs, activity logs, and state snapshots.

Design principles

File system as state bus

.tns/ stores manifest, sections, reviews, handoff, locks, and activity as JSON, JSONL, and Markdown.

Natural language to contract

tns compile turns task/config into program.json, making sections, validators, permissions, and external tools explicit.

Agent-as-coprocessor

The agent doesn't control the loop. AVM assigns one section, the agent returns structured results, the runtime decides the state transition.

Staged validation

preflight, pre_step, post_step, and post_run can each bind validators and command sets, with policy deciding block vs. fix vs. freeze.

Architecture

task.md + tns_config.json
        │
        ▼
tns compile ───────────────► .tns/compiled/program.json
        │
        ▼
tns run/start ──► executor ──► verifier ──► policy transition
        │             │            │
        ▼             ▼            ▼
.tns/sections.json · reviews.json · handoff.md · activity.jsonl · locks/

The CLI layer provides init, compile, simulate, run, start, status, btw, approve, recover, and more. The core layer handles workflow, sections, FSM, agent bridge, state, runtime, policy, permissions, validators, and the command bridge.

AVM ISA

The AVM FSM program has four state types: task, decision, loop, and terminal. Each state can declare on_enter instructions and conditional transitions. The ISA is intentionally small so orchestration remains readable, simulatable, and auditable.

OpcodeTypeSemantics
setdataWrite a value to a context dotted path.
inc / decdataIncrement or decrement a numeric register (retry, budget, loop counter).
appenddataAppend an event or intermediate value to an array path.
ifcontrolExecute then/else instruction blocks based on a condition.
whilecontrolBounded loop with max_iterations to prevent unbounded expansion.
emitside effectWrite an event to the simulation trace.

State inventory

Key state files are not hidden caches — they are the runtime surface that both operators and tools can read directly.

FilePurpose

Validation and policy

AVM removes "acceptance" from the agent's self-assessment. Validators can check file existence, text regex, JSON paths, and command-set results. Policy then decides whether failure means block_section, mark_needs_fix, freeze, or fail_run. Failure becomes a routable state, not a line in a log.

Permissions and locks

Permission profiles match allowed bash commands, workspace-only path audit, and approval tags per section. High-risk steps freeze the workspace until the operator authorizes them with tns approve --tag .... All mutating flows use named locks under .tns/locks/, with PID and timestamp for stale-lock detection.

Recovery model

The runtime continuously writes a heartbeat. If a single Claude follow session exceeds monitor.max_agent_runtime_seconds, the watchdog marks it as retryable. tns recover cleans up stale runtime, locks, and lingering in_progress sections. When all sections are terminal, semantic recovery can release locks directly.

Validated case

The audiobook-video template is a real-machine proof of the AVM approach: it splits "English adaptation + manifest," "media generation," and "deterministic edit + QA" into three sections, with validators and approval boundaries for external tools, asset files, ffmpeg output, and video checks. This case demonstrates that TNS isn't just for code tasks — it handles production pipelines with generative assets, CLI tools, and strict acceptance criteria.
