Token Never Sleeps Command Reference & Usage Guide

This document covers install, initialization, compilation, running, monitoring, permission approvals, recovery, FSM simulation, and template cases. Assumes Node.js 22+ and the claude CLI available in your PATH.

Package: token-never-sleeps Node.js 22+ tmux optional

Install

npm install -g token-never-sleeps
tns help

tns is a pure-TypeScript npm CLI. It preserves the local runner, state tracking, executor/verifier workflow, tmux-aware startup, plan import, artifact index, and workspace templates.

Quick start

tns init --workspace ./my-task
cd ./my-task

tns compile --config ./tns_config.json
tns doctor --config ./tns_config.json
tns status --config ./tns_config.json
tns run --config ./tns_config.json --once

init writes task.md, tns_config.json, and the .tns/ directory. Before the first run, compile and doctor are recommended: the former produces a readable orchestration program, the latter checks config, binaries, tmux, and workspace preflight.

Common loop

# manual stepping
tns run --config ./tns_config.json --once

# long direct loop
tns run --config ./tns_config.json

# choose managed tmux when configured, otherwise direct
tns start --config ./tns_config.json

# read-only live snapshot during long runs
tns btw --config ./tns_config.json --events 12 --reviews 5

Command reference

tns initCreate a workspace, task, config, and .tns/ state directory.
tns compileCompile task/config into .tns/compiled/program.json.
tns simulateSimulate the config or compiled FSM program; use --set key=value to inject context.
tns doctorRun config, binary, tmux, and preflight diagnostics.
tns statusRead and report sections, freezes, approvals, artifacts, locks, tmux, and runtime.
tns btwRead-only snapshot — doesn't acquire the workspace lock. Ideal for observing long tasks.
tns runRun the TNS loop directly; --once advances only one round.
tns startChoose managed tmux or direct runner based on configuration.
tns run-tmuxExplicit tmux mode; fails fast when tmux is unavailable.
tns approveGrant a named permission tag to unblock a frozen high-privilege step.
tns revokeRevoke a previously granted tag, affecting future runs.
tns traceView recent activity events, validator outcomes, and section trajectory.
tns recoverClean up stale runtime, stale locks, and lingering in_progress sections.
tns plan-importImport a markdown plan into tracked sections.
tns freezeManually freeze the workspace.
tns unfreezeLift a freeze state.

Compile and synthesis

tns compile --config ./tns_config.json
tns compile --config ./tns_config.json --synthesize
tns compile --config ./tns_config.json --synthesize --apply

The compile output ensures the executor/verifier never improvise the task structure. --synthesize invokes the compiler agent to produce a structured patch for preflight, permissions, validators, command hooks, policy, and externals. --apply merges the patch back into config and recompiles.

FSM program — manual authoring over compiler agent

tns compile --synthesize relies on a compiler agent to infer task structure. That's convenient for exploration, but for production tasks that demand strict reproducibility, hand-authoring config.program is the more stable approach. A hand-written FSM program doesn't depend on agent inference — it behaves identically on every run and can be directly version-controlled.

State types

StatePurpose
taskExecute a work section, bound to executor/verifier
decisionConditional branch; selects the next transition based on context data
loopBounded loop with max_iterations to prevent unbounded expansion
terminalTerminal state; marks the task as complete

AVM ISA — instruction set

OpcodeTypeSemantics
setdataWrite a value to a context dotted path. E.g. {"set": ["retries", 0]}
incdataIncrement a numeric register (+1) — retry counters, budget tracking
decdataDecrement a numeric register (−1) — countdown, remaining steps
appenddataAppend an event or intermediate value to an array path
ifcontrolExecute then/else instruction blocks based on a condition
whilecontrolBounded loop with max_iterations to prevent infinite loops
emitside effectWrite an event to the simulation trace for debugging and audit

Hand-written example

A config.program defining a simple three-step flow: initialize → conditional branch → execute or skip:

{
  "program": {
    "initial": "init",
    "states": {
      "init": {
        "type": "task",
        "section": "Initialize environment",
        "on_enter": [
          {"set": ["step_count", 0]},
          {"set": ["need_extra", false]}
        ],
        "transitions": [
          {"target": "check_extra"}
        ]
      },
      "check_extra": {
        "type": "decision",
        "on_enter": [
          {"if": {
            "condition": {"path": "need_extra", "op": "eq", "value": true},
            "then": [{"emit": "branching to extra step"}],
            "else": [{"emit": "skipping extra, going to done"}]
          }}
        ],
        "transitions": [
          {"target": "extra_step", "condition": {"path": "need_extra", "op": "eq", "value": true}},
          {"target": "done", "condition": {"path": "need_extra", "op": "eq", "value": false}}
        ]
      },
      "extra_step": {
        "type": "task",
        "section": "Extra processing",
        "on_enter": [
          {"inc": "step_count"}
        ],
        "transitions": [
          {"target": "done"}
        ]
      },
      "done": {
        "type": "terminal",
        "on_enter": [
          {"emit": "task complete"}
        ]
      }
    }
  }
}

Validate the FSM before running with tns simulate:

tns simulate --config ./tns_config.json
tns simulate --config ./tns_config.json --set need_extra=true --compact

Manual authoring vs. compiler agent: the compiler agent is great for rapid prototyping, but its output depends on model inference and may vary between runs. A hand-written config.program is a deterministic artifact — it can be code-reviewed, diffed, checked into git, and costs zero agent tokens. For production-grade tasks, define the FSM skeleton by hand first, and use --synthesize only to fill in supplementary details.

Permissions

{
  "permissions": {
    "default_profile": "standard",
    "profiles": {
      "standard": {
        "permission_mode": "acceptEdits",
        "allowed_bash_commands": ["pwd", "ls", "cat", "sed", "rg", "find", "git", "node"],
        "workspace_only": true
      },
      "media_render": {
        "permission_mode": "acceptEdits",
        "allowed_bash_commands": ["node", "ffmpeg", "ffprobe"],
        "requires_approval": "media-render",
        "workspace_only": true
      }
    },
    "section_profiles": [
      { "match_title": "Deterministic edit and QA", "profile": "media_render" }
    ]
  }
}

When a required approval is missing, TNS freezes the workspace and writes .tns/approvals.json. After human review: 

tns approve --config ./tns_config.json --tag media-render --note "operator reviewed"
tns run --config ./tns_config.json --once

Monitoring and recovery

tns btw --config ./tns_config.json
tns trace --config ./tns_config.json --limit 40
tns recover --config ./tns_config.json
tns recover --config ./tns_config.json --force

btw is the most-used read-only observation surface for long tasks; trace shows event history; recover cleans up stale locks, runtime state, and interrupted sections. The watchdog is governed by monitor.heartbeat_seconds, monitor.max_agent_runtime_seconds, and monitor.kill_grace_seconds.

Practical tips

  • Write task.md with verifiable sections — don't let one section cover exploration, implementation, and QA simultaneously.
  • Use approval tags for external-tool steps; let the agent produce plans and manifests first, then open up generation or render permissions.
  • During long runs, prefer tns btw so monitoring commands don't contend for the runner lock.
  • Re-run tns compile after every significant task/config change so .tns/compiled/program.json stays the stable contract.
  • Write deterministic checks as command hooks or validators rather than relying on the verifier's natural-language judgment alone.
